# ChargePlan API

A thin, stateless layer over the planning engine (`backend/chargeplan/api/app.py`). Nothing is stored. Interactive docs
are generated by FastAPI at `http://127.0.0.1:8000/docs` while the server runs.

| Method | Path | Returns |
|---|---|---|
| GET | `/api/health` | `{"status": "ok"}` |
| GET | `/api/examples` | `[{"key": "hand_checkable", "title": "..."}, ...]`: the bundled synthetic examples |
| GET | `/api/examples/{key}` | One example's inputs, in exactly the shape `POST /api/plan` accepts |
| POST | `/api/plan` | The full result: status, schedule, costs, comparison, explanation |

## Request: `POST /api/plan`

Times are **local clock times at the site, without a UTC offset**. The `timezone` says which offset applies. The night
can be at most 24 hours, and times sit on :00 or :30.

```json
{
  "timezone": "America/New_York",
  "horizon_start": "2026-10-15T18:00",
  "horizon_end": "2026-10-16T08:00",
  "site_limit_kw": 10,
  "efficiency": 0.9,
  "rates": [
    { "start": "2026-10-15T18:00", "end": "2026-10-16T00:00", "price_per_kwh": 0.30 },
    { "start": "2026-10-16T00:00", "end": "2026-10-16T06:00", "price_per_kwh": 0.12 },
    { "start": "2026-10-16T06:00", "end": "2026-10-16T08:00", "price_per_kwh": 0.30 }
  ],
  "vehicles": [
    { "id": "v1", "name": "Van A", "arrival": "2026-10-15T18:00", "departure": "2026-10-15T23:00",
      "energy_needed_kwh": 18, "max_power_kw": 10 },
    { "id": "v2", "name": "Van B", "arrival": "2026-10-15T18:00", "departure": "2026-10-16T08:00",
      "energy_needed_kwh": 18, "max_power_kw": 10 }
  ]
}
```

```bash
curl -s -X POST http://127.0.0.1:8000/api/plan -H 'Content-Type: application/json' --data @plan.json
```

```json
    "total_cost": 8.4,
    "grid_kwh": [[0, 0, 0, 0, 0, 0, 5, 5, 5, 5, 0, "..."], ["..."]],
    "site_kw": [0, 0, 0, 0, 0, 0, 10, 10, 10, 10, 0, "..."],
    "vehicles": [{ "id": "v1", "name": "Van A", "departure": "2026-10-15T23:00:00-04:00",

  "comparison": { "comparable": true, "optimized_cost": 8.4, "baseline_cost": 12.0,
                  "savings": 3.5999999999999996, "savings_pct": 0.3,
                  "note": "Both plans ready every van with the same energy." },

```

Numbers come back at full precision (`3.5999999999999996`); the app rounds only for display. Result times carry the
site's UTC offset.

## Status values

| `status` | Meaning | HTTP |
|---|---|---|
| `optimal` | Every van ready; the solver proved this is the lowest modeled energy cost | 200 |
| `infeasible` | The inputs are valid, but no schedule readies every van. `infeasibility_reasons` says why when it can | 200 |
| `invalid` | The inputs don't make sense as a plan. `issues` lists `{field, message}`, e.g. `vehicles[1].departure` | 200 |
| `solver_limit` / `solver_error` | The solver stopped or failed. This is **not** proof the plan is impossible | 200 |

Requests that aren't well-formed JSON of the right shape get **422** (with the field that's wrong). Bodies over 64 KB get
**413**. Domain problems are never HTTP errors: they come back as `invalid` with messages written for the user.
